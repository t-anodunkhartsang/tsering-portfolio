# Project Domain Model

## Goal

The first application domain model represents portfolio projects.

A project contains the information required to display project cards and,
later, detailed project case-study pages.

The implementation follows a database-first migration workflow:

1. Define the database schema with Flyway.
2. Apply the migration to PostgreSQL.
3. Map the schema to a JPA entity.
4. Let Hibernate validate that the mapping matches the database.

---

## Project Data Model

The initial `projects` table contains:

| Column | Type | Purpose |
|---|---|---|
| `id` | `BIGINT` | Internal primary key |
| `slug` | `VARCHAR(150)` | Unique URL-friendly project identifier |
| `title` | `VARCHAR(200)` | Project title |
| `short_description` | `VARCHAR(500)` | Summary used on project cards |
| `description` | `TEXT` | Full project description/case study |
| `github_url` | `VARCHAR(500)` | Optional source-code URL |
| `live_url` | `VARCHAR(500)` | Optional deployed application URL |
| `image_url` | `VARCHAR(500)` | Optional project image |
| `featured` | `BOOLEAN` | Controls featured-project display |
| `display_order` | `INTEGER` | Manual project ordering |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | Creation timestamp |
| `updated_at` | `TIMESTAMP WITH TIME ZONE` | Last-update timestamp |

---

## Flyway Migration

The initial schema is defined by:

`backend/src/main/resources/db/migration/V1__create_projects_table.sql`

```sql
CREATE TABLE projects
(
    id                BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    slug              VARCHAR(150) NOT NULL UNIQUE,
    title             VARCHAR(200) NOT NULL,
    short_description VARCHAR(500) NOT NULL,
    description       TEXT NOT NULL,
    github_url        VARCHAR(500),
    live_url          VARCHAR(500),
    image_url         VARCHAR(500),
    featured          BOOLEAN      NOT NULL DEFAULT FALSE,
    display_order     INTEGER      NOT NULL DEFAULT 0,
    created_at        TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at        TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT projects_display_order_non_negative
        CHECK (display_order >= 0)
);
```
Flyway applied this migration and recorded it in:

```flyway_schema_history```

The migration was verified as version 1 with status success = true.

---

## Why Use a Slug?

The database has both:

```id```

and:

```slug```

The database ID is intended for internal identification.

The slug is intended for externally readable URLs.

For example:

```/projects/tibetan-dharma-community-hub```

The `slug` column therefore has a `UNIQUE` constraint so that each project can
be addressed unambiguously.

---

## Database Constraints

The database enforces several integrity rules.

### Primary Key
```sql
PRIMARY KEY (id)
```
Every project has a unique internal identifier.

### Unique Slug
```sql
UNIQUE (slug)
```
Two projects cannot use the same public slug.

### Required Fields
Important fields use:
```sql
NOT NULL
```
so invalid incomplete project records cannot be persisted.

### Display Order
```sql
CHECK (display_order >= 0)
```
prevents negative ordering values.

These rules are enforced at the database level instead of relying entirely on
application code.

## JPA Entity

The SQL table is mapped to:

`ch.tsering.portfolio.entity.Project`

The class is annotated with:
```Java
@Entity
@Table(name = "projects")
public class Project(){
}
```
`@Entity` marks the class as persistent JPA data.

`@Table(name = "projects")` explicitly maps the class to the PostgreSQL
`projects` table.

---

## SQL and Java Naming

Java uses camelCase while SQL uses snake_case.

For example:
```
Java                PostgreSQL
-----------------------------------
shortDescription    short_description
githubUrl           github_url
liveUrl             live_url
imageUrl            image_url
displayOrder        display_order
createdAt           created_at
updatedAt           updated_at
```
Explicit `@Column` mappings are used where the names differ.

Example:
```Java
@Column(name = "short_description", nullable = false, length = 500)
private String shortDescription;
```

## Type Mapping
The initial Java/PostgreSQL mappings are:

| Java             | PostgreSQL                 |
| ---------------- | -------------------------- |
| `Long`           | `BIGINT`                   |
| `String`         | `VARCHAR` / `TEXT`         |
| `boolean`        | `BOOLEAN`                  |
| `int`            | `INTEGER`                  |
| `OffsetDateTime` | `TIMESTAMP WITH TIME ZONE` |

`OffsetDateTime` was selected for the timestamp fields because the database
columns use `TIMESTAMP WITH TIME ZONE`.

---

## Identity Generation
The database column is defined as:
```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```
The Java mapping is:
```Java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```
The database therefore generates project IDs rather than requiring the
application to manually assign them.

---

## Schema Ownership

Flyway owns the database schema.

Hibernate is configured with:
```Yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```
The responsibility is therefore:
```
Flyway
   ↓
Create and modify database schema

Hibernate
   ↓
Validate Java mappings against database schema
```
Hibernate does not automatically create or modify application tables.

This makes database changes explicit and version-controlled.

---

## Migration Immutability

After a Flyway migration has been successfully applied, it should generally not
be edited.

For example, if the project later requires a `status` column, the original:

`V1__create_projects_table.sql`

should remain unchanged.

A new migration should instead be introduced:

`V2__add_status_to_projects.sql`

This preserves a reproducible history of the database schema.

---

## Verification
After creating `Project.java`, the Spring Boot application started successfully
with Hibernate schema validation enabled.

This confirms that Hibernate considers the JPA entity mapping compatible with
the PostgreSQL schema created by Flyway.

A successful schema validation does not mean every business rule is represented
in Java. Database-specific constraints and default behavior can still exist
independently of the entity mapping.

---

## Timestamp Note
The database currently defines:

```sql
updated_at TIMESTAMP WITH TIME ZONE
    NOT NULL DEFAULT CURRENT_TIMESTAMP
```
The default is applied when a row is initially inserted.

It does not **automatically change every time the row is updated**.

Application-level update handling will therefore be added later, for example
through JPA lifecycle callbacks or explicit service logic.

---

> **Architectural principle:** Database structure is managed explicitly through
versioned migrations. Java entities represent and validate that structure but
do not implicitly control schema evolution.
